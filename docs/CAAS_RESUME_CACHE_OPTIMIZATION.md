# CAAS resume cache optimization

Deferred until the ongoing malignant and neoplasia runs have finished. Do not
change the CAAS task keys or restart these runs to apply this optimization.

## Finding

On November 3, 2026, a resumed malignant run reused 1,701
`CAAS_CORE:CAAS_CORE_BATCHED` tasks. The cache pass ran from approximately
14:29:35 to 14:36:52. The `b0_observed` and `b0_observed_strict` missing-output
debug messages for `blk_*` tasks are expected: these optional outputs are
generated by the observed `b0` tile, not permulation blocks.

In `subworkflows/CT/caas_permulation.nf`, each tile evaluates
`scoringInputHash(params.caas_map_dir)` when generating its task script. For
this run, the MAP directory held 16,068 files. The fingerprint traverses the
directory and incorporates file names, sizes and modification times; it does
not read and hash the MAP file contents. Across 1,701 tiles this can require
about 27.3 million file-entry checks, versus 16,068 for one traversal.

The repeated traversal is a strong candidate for part of the resume overhead,
not a measured attribution of the entire cache-pass time. An independent
Python traversal of the directory took about 20 seconds under the then-current
filesystem load; it is not directly comparable to Nextflow's concurrent
Groovy operations. Other cache-key construction, file metadata and output
checks will remain after the optimization.

The implementation-source fingerprint is also recalculated for each tile.
Assess its cost separately before optimizing it.

## Proposed approach

Calculate the **same** MAP fingerprint once per workflow invocation, and
reuse that value for all tiles. This reduces repeated enumeration while
preserving the existing input-sensitivity policy, provided the MAP directory
does not change during the run. Do not replace the fingerprint with a new
algorithm, change the task inputs, or change the rendered task script as part
of this optimization.

## Cache safety

The fingerprint value is interpolated in `scoring_source.sha256` in each
`CAAS_CORE_BATCHED` task script, and therefore affects the task cache key. The
generated script, all inputs, process identity and source-fingerprint values
must remain identical for existing cache entries to be reusable.

`subworkflows/CT_DISAMBIGUATION/ct_observed.nf` is itself read by
`observedSourceHash()`, which contributes to `coreScoringSourceKey()`. Editing
that file can therefore invalidate CAAS tasks even when its behavior appears
unchanged. Avoid modifying it for this optimization. Also check all other
explicitly fingerprinted source paths before choosing where to implement it.

A local Nextflow 25.10.3 toy test changed a helper's implementation while
keeping its returned value and the generated task script identical; `-resume`
reported the task as cached. That demonstrates the principle only; it is not
a guarantee for this workflow or the cluster's Nextflow version.

## Validation before use

1. After the ongoing runs finish, preserve their cache and work directories.
2. Test on an isolated copy or representative fixture, not the production run.
   Verify the old and new fingerprints are byte-for-byte identical for the same
   MAP snapshot, including empty and missing-directory cases.
3. Compare rendered task scripts and Nextflow task hashes for representative
   `b0` and `blk_*` tiles. Run a controlled `-resume` and confirm they are
   reported as cached, with no new CAAS replay submissions.
4. Measure controller time and filesystem activity before and after; report
   the result separately from the theoretical reduction in metadata scans.
5. Verify that a MAP metadata change between runs still changes the fingerprint
   and invalidates the intended tasks. Document that mutations during a single
   run are not detected after the once-per-run fingerprint is computed.
